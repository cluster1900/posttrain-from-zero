# 第 3 章 第一版为什么不能用：从 v1 到 v2（10-10 起）

## 动机

### 先问一个比 loss 更早的问题

如果一个训练程序能加载模型、读取任务、打印奖励，最后还能保存 checkpoint，它是否已经完成了强化学习？本项目的第一版给出了反例：这些动作都可以发生，但模型没有根据奖励做过一次参数更新。

2026-10-10 的审核结论很直接：v1 工程不能产出有效训练结果。最严重的问题不是超参数不够好，而是 `train/rl_trainer.py` 中的回答来自硬编码的 `dummy_response`。训练循环里没有真实生成、行为 log-probability、策略损失和反向传播，最后却保存了标为完成的权重。继续给这样的程序增加运行步数，不能补上缺失的学习链路。

这是本章的起点。重写 v2 要解决的，是让“任务输入 → 模型行动 → 环境反馈 → 损失 → 参数更新 → 可核验评测”成为真的连通链路。源记录还明确指出：工具格式、模型依赖、数据入口、沙箱和评测都存在阻断性问题，因此仅替换 RL 循环也不够。出处：`docs/apexo/00_progress.md` §1.2，提交 `ca57456`；历史实现 `train/rl_trainer.py`，提交 `047c932`。

### 读者在 CPU 上运行的最小审计

在已按第 1 章装好固定教学依赖的本书目录运行：

```bash
python3 examples/ch03_audit.py
python3 -m pytest tests/test_ch03_audit.py -q
```

程序不联网、不下载模型、不启动沙箱、不运行模型生成的命令，也不保存 adapter。它把审核拆成三种证据：

1. 静态扫描一段人为构造的源码，标出硬编码 `dummy_response`、缺少直接 `backward()` 调用和缺少直接 `step()` 调用。扫描器不执行被检查的代码。
2. 在 CPU 上构造一个标量参数，分别观察不反传、只反传、真正更新和主动跳过四种情况。参数初值 `0.0`、目标 `2.0`、学习率 `0.1` 都是教学数值；更新后的约 `0.4` 也不是本项目训练指标。
3. 检查人为构造的评测输入：没有 trial 时返回退出码 `2`，不创建新报告；缺少 timing、任务集合不一致或奖励非法时拒绝输入。完整 fixture 只能得到 `EVIDENCE_READY_DEMO_ONLY`，绝不产生正式门禁的 `PASSED`。

下面两行与示例函数 `write_demo_evidence` 逐字一致，是只供说明的函数内片段，不是独立可运行程序：

```{.python .source-excerpt}
    if not trials:
        return 2
```

对应出处是本书 `examples/ch03_audit.py`，不是源项目逐字摘录。真实源项目的同类约束见 `evaluation/run_eval.py` 与进度台账 §1.2。这里使用 `.source-excerpt` 标记，是为了让构建与代码检查知道它不能脱离函数单独执行。

预期输出中，`dummy` 被归类为 `NO_BACKWARD_EVIDENCE`，`backward_only` 为 `NO_PARAMETER_CHANGE`，`update` 为 `TOY_UPDATE_OBSERVED`，`skip` 为 `SKIPPED_NOT_UPDATED`。这些标签刻意不使用“RL 训练成功”。

需要保留两条边界。第一，静态扫描能抓明显空壳，却不能证明调用实际发生：把 `backward()` 和 `step()` 放进永远不执行的分支，扫描仍然可能放行，测试专门保留了这个反例。第二，真实 RL 中零方差组、全掩码或其他明确条件可能合法跳过更新，不能要求每步参数都变化；应把“为什么跳过、跳过了多少”记清楚，不能把全部跳过的运行描述为已发生有效策略更新。

另外，“本次不写报告”不等于“目录中没有旧报告”。示例测试验证空输入不会覆盖既有文件。实际流水线必须检查本次退出状态、运行身份和报告来源，不能仅凭旧文件还在就继续晋级。

## 坑与修复

### 第一层：从“像训练”改成真的存在训练链路

先把 v1 的 P0/P1 逐条讲清。这里的严重性是审核报告的分类，不是本书按结果重新划分。

**RL 空壳为什么危险。** 模型载入、优化器创建、任务循环、奖励日志和最终保存，每一项单独看都像训练系统的组成部分。但是 `dummy_response` 使行动与策略参数脱钩；没有 logprob、损失和反向传播，又使奖励与参数更新脱钩。审核需要沿着数据依赖追踪，而不是数目录里有多少文件。

**格式错误为什么不只是解析小问题。** SFT 给模型看的格式、rollout 增量追加的格式和 serving 的格式若不一致，模型可能在训练时学一种边界，在推理时遇到另一种边界。v2 用统一 Jinja 模板与原生 XML 参数形式，并测试增量拼接和整段渲染等价。聊天模板的细节留到第 5 章。

**SFT 为什么不能只修到“不崩”。** 缺少 collator 会让不同长度的样本在 `bs>1` 时无法按预期组批；简单裁切超长轨迹又可能裁掉末尾提交或最终反馈。v2 改为单样本微步加梯度累积，用本次更新所有有效 token 的总数归一化，并整条丢弃超长样本。这分别修复组批、损失权重和轨迹完整性，不能只靠把 batch size 调小就认为全都解决了。

**评测假成功为什么比报错更糟。** v1 在没有真实结果文件时自动构造模拟样本，再把它们送入正常裁决和报告写入路径。教学 fixture 本身有价值，但必须与生产输入分开；一旦代替真实日志进入晋级门禁，报告就失去了证据意义。v2 的缺结果路径返回退出码 `2`，不生成新报告。

| 现象 | 根因 | 修复 | 证据 |
| --- | --- | --- | --- |

### 第二层：输入、恢复和空更新也必须可核验

测试不只验证主路径，还揭示“看似边角、实际上改变实验含义”的问题。恢复时换了一份 manifest，使用同一份 checkpoint 名称也不能说明还是同一个实验；冒烟只有循环完成而没有任何有效轨迹，也不能宣称跑通了训练链路。

### 第三层：把单卡串行做成真实的内存与权重协议

“训练与推理串行”不是只把两个函数写成先后调用。只要训练器、优化器状态和输出头副本仍留在 GPU，vLLM 分配缓存时就会与它们竞争显存。反过来，如果推理引擎继续占着需要的物理内存，训练 forward 也没有空间。

第二轮审核把生命周期写具体：生成阶段将 HF 训练器和 Adam 状态移到 CPU；更新前让 vLLM sleep，再把训练器搬回 GPU。冻结输出头只保留 CPU 主副本，按训练阶段传输。图 3-3 表达的是阶段归属，不是按比例绘制的显存图，也没有宣称这组配置当时已在 40GB 卡上通过。

![图 3-3　生成与更新两阶段的资源归属（示意，不表示显存大小或耗时）](images/ch03_memory_phases.svg)

权重同步也要单独验收。训练器改了 LoRA，不代表 vLLM 已经生成自新策略。需要明确推送的张量、HF 与 vLLM 的命名映射、缓存唤醒与失效顺序，再检查同一 token 的 logprob 差。只看到同步函数返回而没有对应数值，不足以证明训练和采样用的是同一策略。

| 现象 | 根因 | 修复 | 证据 |
| --- | --- | --- | --- |
| `test.sh` 非零退出后，已有奖励被清成 0 | 把脚本退出码和 verifier 奖励合同混为一谈 | 按奖励文件判分；超时与 OOM 仍为 0，不把失败测试误当基础设施成功 | `00_progress.md` §6.2 |
| GDN 部分门控未进入 LoRA 目标 | 漏了 `in_proj_a`、`in_proj_b` | 将两者加入目标模块，并检查可训练参数 | `00_progress.md` §6.2；`configs/rl/qwen35_2b.yaml`，提交 `fbf621e` |
| 生成与更新虽串行调用，显存仍叠加 | HF 训练器和 Adam 状态未离卡，vLLM 仍占用缓存 | 生成前 offload；更新前 vLLM sleep，随后搬回训练器 | `00_progress.md` §6.2；风险 R14 |
| 更新后采样仍可能使用旧权重或旧缓存 | 权重推送和 KV/prefix cache 时序不可靠 | 一次推完权重；KV cache 唤醒后再 reset prefix cache；策略已偏离 Base 时同步差 > 0.5 失败退出 | `00_progress.md` §6.2；风险 R4 |

### 第四层：在 GPU 冒烟前补上失败路径

第四轮审核继续处理一些特别容易“静默出错”的分支。比如 Python 的 `zip` 按较短输入结束，生成器少返回一条时，程序不一定崩溃，反而可能悄悄丢任务。再如容器 `Running=false` 只能说明没有运行，不能直接证明它曾被 OOM killer 杀掉。审计必须核对这些状态的准确含义。

| 现象 | 根因 | 修复 | 证据 |
| --- | --- | --- | --- |
| vLLM sleep allocator 与可扩展分配器冲突 | 独立内存池与 `expandable_segments` 不兼容；旧/新环境变量别名可能同时存在 | 第四轮先处理旧别名；后续 R17 明确在 CUDA 初始化前同时清理两种变量中的冲突选项，不能只改变量名 | `00_progress.md` §6.4；`06_risks_and_decisions.md` R17，提交 `ca57456` |
| 导出可用的键名不一定能直接用于 vLLM 同步 | HF 的 `model.layers.*` 与运行时的 `language_model.model.layers.*` 属于不同布局 | 官方 safetensors 导出与运行时同步分别显式映射；开启 hybrid cache 所需的 chunked prefill | `00_progress.md` §6.4；风险 R4、R11 |
| 声称输出头 CPU 常驻，实际仍留约 2–2.5GB 在 GPU | 从已在 GPU 的模型复制后才尝试 pinned，未先确保 CPU 归属 | 显式先 `.to("cpu")` 再 pinned，按训练阶段搬运 | `00_progress.md` §6.4；`train/rl_trainer.py`，提交 `fbf621e`；风险 R18；容量为记录中的近似说明，不是本章峰值测量 |
| 缺 timing 或不同任务集也被比较为可比实验 | 允许缺失/损坏 `timing.json`；只取 baseline/current 任务交集 | SFT/RL 门禁要求 timing 完整可解析、任务集合相同，并加回归测试 | `00_progress.md` §6.4；风险 R19 |
| 总 token 超预算，或短 batch 被静默丢弃 | 合成结束 token 没有预留位置；`zip` 会截到较短序列 | 为合成轮次结束符留 1 个 token；硬校验返回 batch 长度 | `00_progress.md` §6.4；`train/rollout.py` |
| 正常退出容器被误记 OOM | 用 `Running=false` 代替 OOM 证据 | 只按 Docker 的 `OOMKilled=true` 或状态查询失败作相应保守标记 | `00_progress.md` §6.4；`train/sandbox.py` |
| 生成器、沙箱或 batch 校验异常后残留容器 | 异常分支没有覆盖所有已启动环境 | 用清理栈保证异常时也关闭已启动 Docker 环境 | `00_progress.md` §6.4；`train/rollout.py` |
| A100 配置有误时静默落到 CPU 长跑 | 训练入口未强制验证 CUDA | 在 SFT 前检查 CUDA，不满足就失败 | `00_progress.md` §6.4；`scripts/train_a100.sh` |
| 同一 CPU 测试随 Hub 更新漂移 | 分词器 fixture 取可变 `main` | 固定到 2B Base revision | `00_progress.md` §6.4；`tests/conftest.py` |
| 任务包解到一半，仍形成“完整”但缩小的 manifest | 下载/解包完成性与任务文件合同未强制校验 | 临时目录解包后原子改名；写 revision 与 tarball SHA-256 标记；缺文件或实例不一致硬失败 | `00_progress.md` §6.4；`scripts/data/prepare_apexo_rl.py` |
| 官方 Base 未经 SFT 就默认进入 RL | 没有建立所需交互格式，可能全零组而无有效梯度 | 默认拒绝原始 Base 直接 RL；标准入口先 SFT，再传 `final_adapter`；诊断例外必须显式配置 | `00_progress.md` §6.4；`train/rl_trainer.py`，提交 `fbf621e` |

### 风险登记中仍需带到下一阶段的约束

R1、R4–R6、R9–R11、R13–R14、R17–R19 已在上表对应到具体审核修复。下面补齐早期风险登记里的其他约束。它们是设计风险与后续验收要求，不表示 10-10 至 10-11 已逐个发生过事故；风险表在后续持续更新，不能把其中最新部署方案说成最初部署方案。

| 现象 | 根因 | 修复 | 证据 |
| --- | --- | --- | --- |
| R2：镜像拉取失败或耗时变大，影响 rollout | Docker Hub 限速、镜像缓存和磁盘压力属于基础设施，不是策略能力 | 单独记录 infra；后续按需拉取与磁盘压力清理；不把拉取失败当模型失败奖励 | `06_risks_and_decisions.md` R2；本章未验证实际镜像拉取耗时 |

| R8：不再输出合法工具调用 | 格式行为可能在 RL 中塌陷 | 监控无调用率与格式错误；触发门禁或回滚，而不是只记录 loss | `06_risks_and_decisions.md` R8 |
| R12：导出模型启用 MTP 后可能行为不符 | `mtp.*` 没有随训练更新 | serving 不启用 MTP，报告说明这一边界 | `06_risks_and_decisions.md` R12 |
| R15：短上下文配置在长任务上有局限 | 本项目 RL 的 2B 24K / 4B 16K 长度短于记录中对照的约 65K 长度 | 明示这一取舍；不把短长度 smoke 推广为长上下文已验 | `06_risks_and_decisions.md` R15；`00_progress.md` §6.2 |
| R16：SFT/RL 或 held-out 边界被混用 | 数据源和任务身份若未核验，评测可能泄漏 | 按任务身份检查重叠，按 held-out 清单剔除，并执行 manifest 校验 | `06_risks_and_decisions.md` R16；具体冻结验收见第 4 章 |

R5 还有一条不能被“用 fp32 head”一句话盖住的边界：训练端使用 fp32 输出头，不代表 vLLM 输出头也被改成 fp32。风险登记明确保留了推理端 bf16 与训练端的数值差异，要求通过 `sync/logprob_abs_diff` 验证，不能把 DPPO mask 当成任意权重失配的补丁。R4 的大幅漂移失败退出与 R5 的小幅数值差是两个层次。

## 教训

### 从数据依赖追问，不从文件名推断

`rl_trainer.py`、`optimizer`、`checkpoint` 都只是名字。审核要能回答：行动是不是模型生成的？奖励是不是来自目标环境？当前策略和行为策略的 logprob 各在哪里？哪一项 loss 对哪些参数反传？`optimizer.step()` 是否真的执行？更新后采样引擎是否拿到新权重？v1 正是在这些连接处断开，所以“程序正常退出”无法替它作证。

对读者最小可复用的做法，是同时保留静态与动态证据。静态阅读找明显占位和遗漏；动态检查有效 token、梯度、实际参数变化、跳过原因、同步数值。两类证据各有盲点，不能互相替代，更不能替代最终质量评测。

### 把“不知道”写成系统允许的结果

缺少结果不是零分，也不是通过；它首先是缺证据。缺少 timing、任务集合不同、无有效轨迹、KL 样本缺失，都应阻断相应结论。失败关闭的价值在于让下一步无法借一个漂亮文件名继续前进。

教学数据可以检验解析器，tiny 模型可以验证反向路径，CPU fixture 可以覆盖异常分支。但它们必须带清晰的身份和范围。程序本身把教学证据写成 `DEMO_ONLY`，比在旁边口头说一句“这只是模拟”更可靠。

### 修复后仍需承认尚未验证

PR #1 的交付不是“已在 A100 上训练成功的模型”，而是经过 CPU 验证的 v2 工程，以及明确待完成的 GPU、vLLM 和 Harbor 验收。依赖版本后来仍暴露安装冲突，分配器规则还要继续修正，正说明 CPU 全绿之后仍有环境层面的未知。

配置、运行、测量与结论应分开保存：配置写打算做什么，运行记录写实际做了什么，日志证明发生了什么，门禁再说明这些证据足以支持什么结论。只有这四层对得上，后面的 loss、奖励和评测分数才值得讨论。

### 下一步不是直接长跑

本轮审核已经把数据版本、模板、SFT→RL adapter 接力、恢复和门禁连成一份可检查的合同。接下来先把公开数据固定成可核验 manifest，再验证真实环境中的短链路。第 4 章讲数据冻结，第 5 章讲格式一致性；本章尚未完成的 GPU 与沙箱问题，会随着后续实验逐项暴露并修正。
