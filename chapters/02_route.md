# 第 2 章 后训练全景与本项目的路线

上一章解释了梯度怎样从 loss 走到可训练参数。本章换一个角度：**这个 loss 的监督信号从哪里来？** 同样是在更新语言模型，模仿一段成功轨迹、比较两份回答的偏好、让模型实际执行任务后再按结果学习，是三种不同的数据闭环。分清它们，才能看懂项目为什么先准备数据、再做 SFT，最后才接真实环境。

本章的通用算法解释与项目记录分开。前者给读者一张地图，不表示本项目把地图上的方法都跑过；后者以源仓库提交 `ca57456` 为证据。本项目没有给出 DPO、PPO、GRPO 与 Apexo RL 的公平对照实验，因此这里不排列算法优劣，也不把最后的 pass@1 变化解释成某个算法家族的普遍结论。

## 2.1 从“预测下一个 token”到“把任务做完”

预训练主要让模型从大量文本中学习下一个 token 的条件分布。给定前文，模型把概率分配到词表中的候选 token；训练用已出现的后续 token 作监督。它能学到语言和代码模式，但“能续写代码”与“能在一个陌生目录里检查文件、执行命令、读报错、修正后提交”不是同一个验收条件。

本项目的目标不是训练一个只输出最终答案的聊天模型，而是终端智能体。用户任务进入模型上下文，模型生成 bash 工具调用；环境执行调用，把标准输出、错误与退出状态返回给模型。模型根据新观测继续行动，直到提交、没有合法工具调用或触及预算等终止条件。最终 verifier 检查环境状态并产生分数。这里既有文本生成，也有状态变化：一句看似正确的“文件已经修好”不会自动改写磁盘。

来源：源仓库 `docs/apexo/01_architecture.md` §1、§3.2，`docs/apexo/09_custom_training_design.md` §3.3，提交 `ca57456`。下图为职责示意，不是耗时或性能图。

![图 2-1　终端智能体的一轮交互：模型给出行动，环境返回观测，提交后由 verifier 判分。](images/ch02_agent_loop.svg)

理解这个循环，先区分三个对象。

- **任务**：需要完成的目标，以及任务目录、镜像、验证脚本等固定材料。同一任务可以尝试多次。
- **轨迹**：一次尝试中的完整交互序列。它包含提示、模型生成、工具观测以及终止结果，不等于一条 bash 命令。
- **奖励**：本项目训练合同中的结果信号。源设计规定先把 verifier 分数限制在 `[0,1]`，训练时 `score >= 1.0` 记为 1，否则记为 0。中间分不作为连续训练奖励；基础设施异常还要单独处理，不能把“镜像没拉下来”当成模型做错题。

这里的 outcome-only 指监督来自最终结果，并不是每个中间命令都获得一条人工步骤评分。结果反馈很稀疏：一条长轨迹失败，只告诉我们最后没通过，并不直接说明第几个 token 导致失败。这是后面需要分组比较、过滤和日志诊断的背景。

提交也不是模型在思考里提到某个词就算提交。源设计只在 **bash 执行输出**出现提交标记时触发判分，提交时才上传测试文件，再读取 verifier 产物。把测试提前暴露给模型或接受它自己写的分数，会改变我们要测的任务。此处只解释边界，完整沙箱与 reward hacking 防护放在第 10 章。来源同上 §3.3，以及 `docs/apexo/06_risks_and_decisions.md` R10。

## 2.2 SFT、偏好优化与在线 RL：监督来自哪里

下面是概念对比，不是本项目跑过的实验清单。

| 路线 | 提供给训练器的信号 | 更新时是否需要新环境交互 | 需要警惕的误解 |
| --- | --- | --- | --- |
| SFT | 已有示范轨迹中的目标 token | 通常直接读取固定轨迹，不必为这次梯度更新运行 bash | 成功示范的似然变高，不保证新任务一定成功 |
| DPO | 同一输入下的偏好回答对，加上参考策略 | 标准离线形式使用已有偏好对，不在每次更新时在线采样环境 | 有偏好排序不等于拥有可信的任务 verifier |
| 在线策略优化 | 当前行为策略采样的轨迹、logprob 与奖励 | 需要生成与环境交互闭环 | 奖励高不自动说明格式、安全性和评测口径都正确 |

**SFT 是先学怎么写出这样的行为。** 在本项目，示范来自公开成功轨迹。模型看到 system/user/tool 提供的上下文，但只对允许训练的 assistant 生成段计算负对数似然。观测是条件，不是要求模型模仿生成的答案。第 1 章的 `-100` mask 就在做这件事；第 4 章会解释为什么一条名义上成功的轨迹，仍可能包含不应训练的 assistant 轮。

**DPO 是用偏好对调整相对倾向。** 标准 DPO 目标比较偏好回答与非偏好回答的策略/参考策略相对对数概率，通过分类式损失更新策略，不需要另训练一个显式奖励模型再跑标准 RLHF 循环。这是 Rafailov 等提出的方法；本项目并未用 DPO 训练，所以不能把本书里的 DPO 简介写成项目曾经放弃它的历史原因。技术出处：[DPO 原论文](https://arxiv.org/abs/2305.18290)。

**在线 RL 是先让当前策略试，再根据结果更新。** 旧轨迹告诉我们以前怎么做；新 rollout 告诉我们当前策略真的会做什么。这样的闭环需要处理行为策略概率、环境失败、截断、奖励方差和权重同步，而不仅仅把 SFT 的数据文件换成另一份 JSONL。

PPO 用采样数据构造策略更新目标，并通过裁剪等机制限制过大的更新。GRPO 在语言模型任务中采用同一问题的多份采样结果形成组内相对信号，避免单独的 critic 带来的资源负担。两者是公开技术背景，分别见 [Schulman 等的 PPO 论文](https://arxiv.org/abs/1707.06347) 与 [Shao 等的 DeepSeekMath / GRPO 论文](https://arxiv.org/abs/2402.03300)。本章只解释关系，不把 GRPO 的所有标准化细节套到本项目的 `centered` 实现上。

DPPO 则把更新约束转向策略分布差异的近似，公开方法包含 Binary 与 Top-K 等形式。技术来源为 [Qi 等《Rethinking the Trust Region in LLM Reinforcement Learning》](https://arxiv.org/abs/2602.04879)。本项目记录的配置是 DPPO 的 binary TV 路径，不代表实现了该论文的所有变体。Apexo 是整个项目的流程名；使用这个名字不会改变 DPO、PPO、GRPO、DPPO 或 LoRA 的既有技术归属。具体外部输入与许可继续列在致谢附录。

## 2.3 项目实际走过的主线

源设计把正式路径规定为：冻结公开数据 → LoRA SFT → 从 SFT adapter 起步的 Apexo RL → 用 Harbor 和 Terminal-Bench 2.0 做阶段评测。数据冻结不是训练，adapter 导出也不是评测；四者有不同的输入、输出和失败判据。

![图 2-2　同一流程中的不同产物：固定数据、SFT adapter、RL adapter 与独立评测报告不能互相替代。](images/ch02_artifacts.svg)

| 阶段 | 消费什么 | 产生什么 | 哪个证据不能被跳过 |
| --- | --- | --- | --- |
| 数据冻结 | 固定 revision 的任务包和轨迹 | 三份 manifest、统计与哈希交接记录 | 数据契约校验通过，字节与记录一致 |
| SFT | 成功轨迹、统一模板、官方 Base | LoRA adapter、优化器/恢复状态、训练指标 | 训练段 mask、token 分母、恢复与导出检查 |
| Apexo RL | SFT adapter、RL 任务、真实环境 | 新 adapter、rollout、奖励和更新指标 | 行为概率/权重同步、有效奖励组、真实 verifier |
| 阶段评测 | 指定阶段的模型与相同基准 | Harbor trial 结果、pass@k、格式指标、门禁报告 | 任务集合、完整日志与当时判定口径 |

为什么本项目要先 SFT？这不是我们事后替作者猜的。`docs/apexo/09_custom_training_design.md` §1.3 明确写着：参考路线的起点已经会使用工具，而本项目用官方 Base；默认要求先 LoRA SFT，`allow_raw_base: false`。记录给出的理由是原始 Base 直接进入稀疏奖励环境容易得到全 0 组，过滤后没有可用更新信号。这个设计理由能支持“先做格式与轨迹预热”，但不能推出“做完 SFT 后每步 RL 都会产生非零奖励”。最终前两步仍全 0，说明预热不是成功保证。

同样，正式系统不能把无沙箱预演的奖励混入训练。源设计里的 `RehearsalEnv` 不执行模型命令，只用构造观测与构造奖励检查推理、同步和更新链路。它能证明代码路径走通，不能证明任务完成；源架构专门把 Colab 预演与真实 Docker/verifier 分开。来源：`docs/apexo/01_architecture.md` §3.4，`docs/apexo/09_custom_training_design.md` §3.3，提交 `ca57456`。

## 2.4 一组奖励怎样变成可用信号

在本项目的 `centered` 设置中，同一任务的有效样本组成一组；每条轨迹的优势是其奖励减去该组均值。把“这一条得到 1 分”改写成“这一条比组内平均更好多少”，就得到用于调整生成概率的方向。

下面的数值是**人为构造的教学例子，不是项目 rollout**。第一组全 0，第二组一半失败一半成功。代码与 `examples/ch02_route.py` 的 `chapter_snippet` 一致。

```python
import torch
rewards = torch.tensor([[0., 0., 0., 0.], [0., 1., 0., 1.]])
advantages = rewards - rewards.mean(dim=1, keepdim=True)
useful = rewards.max(dim=1).values != rewards.min(dim=1).values
assert useful.tolist() == [False, True]
assert advantages[1].tolist() == [-0.5, 0.5, -0.5, 0.5]
```

第一组不是“loss 很小所以已经学好了”，而是没有相对信号。全 1 组也同样没有组内差异，只是含义变成这一批样本都成功。源设计还记录：全解任务进入 `solved` 集合，后续采样可跳过；为了补足有用组，可以有界地再采样，但不是无限等到足够成功为止。

真实训练的过滤比这六行代码复杂。先剔除基础设施失败，再检查有效样本数，再过滤零方差组；长度截断样本可能留在组基线中却不贡献梯度。这些顺序会改变优势，不能把任何 0 分都一视同仁地塞进平均数。`examples/ch02_route.py` 还用一个人工小组验证：把 infra 失败剔除后，基线只由有效环境尝试组成；没有足够有效样本时，整个组被跳过。这个例子没有 vLLM、没有 bash、没有模型权重，只验证信号处理的逻辑。

来源：`docs/apexo/09_custom_training_design.md` §3.5，`train/losses.py`，提交 `ca57456`。本章不给完整 DPPO 损失推导，避免把流程入门变成公式目录；第 9 章再逐行对应损失，第 13 章解释训练信号与门禁。

## 2.5 单卡约束怎样改变工程，而不是改写历史

下面各项是设计文档 §1.3 已经列出的取舍，不是新写的作者事后分析。表中的“默认”是该版本设计/配置值，不保证所有运行都使用同一值；后续章节要按每轮实际记录展开。

| 设计维度 | 项目记录的取舍 | 记录中的理由与边界 |
| --- | --- | --- |
| 训练参数 | 使用 LoRA，而不是全参训练；RL lr `1e-5` | 控制优化器状态、激活与计算预算；这里不推断 r/alpha 的未记录动机 |
| 生成与更新 | 同步 on-policy，每批生成后更新；生成时训练器转 CPU，更新时 vLLM sleep | 串行共享单卡，简化与可复现；不是异步多机吞吐结果 |
| 采样规模 | 默认 `4 prompts × 8 samples`，T=1.0、top_p=1.0 | 单卡吞吐与计算预算；采样条数不等于同时存活容器数 |
| 任务上下文 | prompt 上限 4,096 | 系统提示、工具 schema 和任务说明一起放入上下文，避免正文被较短上限截掉 |
| 轨迹预算 | 2B total 24,576、4B total 16,384；每轮 8,192、最多 50 轮 | 记录中的单卡预算折中；并非所有轨迹都会到达上限 |
| 有用组补采 | 默认最多 3 轮 | 无界补采会让单步时长失控；“最多”不是实际发生次数 |
| 沙箱并发 | 最多 8 个存活环境，结束后滚动补位 | 控制 CPU/内存占用；不能只限制线程池却让更多容器活着 |

配置事实来自 `docs/apexo/09_custom_training_design.md` §1.3、§3.5 和 `configs/rl/qwen35_2b.yaml`，提交 `ca57456`。该文档标题保留 A100 40GB 的生产预算背景；项目中也经历了 Colab 80GB 等不同阶段，不能拿一张设计表冒充全程硬件台账。算力转移、失败与费用在第 8 章分别说明。

一个常见误区是把训练器与推理引擎叫作“同一模型”，便默认它们总有相同参数和概率。实际上它们有不同对象、权重布局与数值路径。每次更新后必须把合并后的策略传给推理端，清理旧缓存，再验证 logprob 一致性。同步失败时，“当前策略生成的样本”这个前提就可能不成立。源架构因此把模板一致性、token 追加、权重同步与指标链路画成一个完整系统，而不是只关心 loss 函数。

## 2.6 能从这条路线得出什么，不能得出什么

作者 2026-10-19 的补充说明选择 2B 是因为“足够小”，4B 完成 SFT 后因成本停止。这些事实可以写，但没有记录的 Base/Instruct 选型动机不能替作者补写。本章不补写这项选型的事后理由；保留“没有当时理由记录”的边界。来源：`docs/apexo/11_timeline.md`“作者补充”，提交 `ca57456`。

最终结果也约束解释。第 0 章已经给出 SFT pass@1 为 1.12%，RL 为 0.90%。因此本项目证明的是一条包含数据、SFT、真实环境 RL 与评测的工程闭环被执行和记录，不是“再加 RL 必然更好”。10 月 19 日修改门禁后得到 PASSED，是判定规则的变化，不是原始任务通过数被改写。后面阅读每一章，都要持续区分三件事：代码能运行、合同检查通过、任务能力提高。
